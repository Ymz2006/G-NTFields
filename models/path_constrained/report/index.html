Camera Follow on a Path

Homotopy head vs metric NTFields on a path-constrained prism · results of 2026-10-21 · repo models/path_constrained/

A camera follows an object moving along a known path and must keep it in view. We model the line of sight as a thin square prism glued to the object at one end, free to rotate, and plan its motion with two learned travel-time fields. The homotopy head solves almost every case. Metric NTFields fails on 8–14% of whole-path cases, mostly right at the start of the path.

The problem

The object is a point moving along a given path p(l), with l the arc length from 0 to L. The camera's line of sight is a square prism (side w = 0.02, length h = 0.2 in normalized room units). One end is glued to the object and the other end is the camera. The prism may turn freely about the glued end. Start and goal orientations are given. If the prism never touches the scene, nothing ever blocks the camera's view of the object, and the camera never hits anything.

The viewer below draws the line of sight as a view pyramid: apex at the camera, base the w × w square around the object. The pyramid sits inside the planned prism, so a clear prism means a clear pyramid.

How the idea was made to work

  • It is SE(3) planning on a slice. The allowed poses are path position × rotation about the object, a 4-d piece of SE(3). Feeding the models the path unrolled onto the x axis makes that slice literal, so both networks, the double cover and the MPPI planner run unchanged.
  • "xyz speed along the path direction" became an exact projection of the Eikonal residual: only the gradient component along the path tangent is kept from the translation part, plus the full rotation part.
  • The clearance speed slows motion along the path too, not only rotation. With speed on rotation alone, sliding along the path costs the same near an obstacle as in free space, so a plan could slide straight through one.
  • Forward-only planning. A camera that follows an object cannot make the object go back, so every MPPI sample keeps dl ≥ 0. This costs nothing in success (below).

Setup

  • Scenes: env1, env3, env4 (rooms with 4, 3 and 6 boxes). There is no env2 mesh on this machine. Clearance is computed exactly for the prism against the boxes.
  • Paths: one smooth path per scene (a), length 1.2–1.5, picked so that turning straight from the start to the goal orientation usually collides; a second path (b) per scene as a check.
  • Test sets (1000 cases each, every case confirmed solvable by an RRT that never moves the object backward): full whole path; tight both ends 0.005–0.02 from the scene; bigrot turn ≥ 150°; hard tight and ≥ 135°; seg sub-paths of at least 0.25.
  • Models: homotopy head (graph_homotopy, double cover, isotropic speed) and the original metric NTFields, each with its own training recipe, 8000 epochs, 800k pairs per scene, 3 seeds.
  • Success: reaches the goal pose within 0.01 and the prism clearance stays ≥ 0 at every waypoint and at 4 sub-steps between waypoints.

Paired case by case (same seed, exact McNemar test), the dual homotopy planner solves 225–514 whole-path cases out of 3000 that NTFields misses, against 0–21 the other way (p < 1e-58 on every whole-path set). On sub-paths the gap is small but still significant: +17/−2, +22/−4, +92/−19.

  • NTFields breaks down near the start of the path. Its collisions happen at a median 2%, 19% and 1% of the path (env1, env3, env4), and its stalls stop by 4–12%. On sub-paths it fails 3–7× more often when the start lies in the first 10% of the path. The likely cause is sparse training data at that end of the path, where fewer random displacements stay on the path.
  • The homotopy head never blocked the view with the dual planner, in any forward-mode evaluation of the main scenes. Its few failures are stalls.
  • Planning both rotation directions matters in env4. The base planner stalls on 7.8% of whole-path cases, all at one place on the path (l ≈ 0.58 L). Planning toward both lifts of the goal rotation and keeping the plan that converges reaches 99.0%, equal to the best of the two directions picked per case.

Harder settings and other paths

One seed each. With the camera farther from the object (prism length 0.3), turning straight works in only 1–5% of cases. The second path per scene (b) uses the prism of length 0.2.

Interactive viewer

models/path_constrained/scripts/path_viser.py is a viser viewer for these plans, built like the other shape viewers. It runs on the lab machine at port 8102 (container pc_viser_path).

  • Pick any of the 27 test sets and filter cases by outcome: both succeed, homotopy only, NTFields only, NTFields collides, NTFields stalls.
  • Both plans play on the same clock (one MPPI step per waypoint). The line of sight is drawn as the view pyramid, the planned prism or both, and turns red where the prism touches the scene. A camera frustum marks the camera.
  • Camera view: a panel renders the scene from the camera end looking at the object, with an adjustable field of view. Look through camera moves your own viewport there, and Opaque obstacles makes occlusion obvious.
  • A clearance-along-the-plan plot for both models, and the results table.
Run it: python models/path_constrained/scripts/path_viser.py --port 8102 (numpy + viser only). The plans come from export_viser_path.py (torch, about 2 min per test set). --look --opaque --dump DIR --strip 6 writes camera-view frames like the strips above.

Caveats

  • The standard whole-path sets were already near 100% for the homotopy head, so the harder variants (tight, bigrot, hard, prism 0.3) were added partway through to separate the models.
  • Second paths, the 0.3 prism and the input-chart comparison use one seed each.
  • The object is a point and the line of sight is a thin prism. The view's width (field of view) is not part of the planning problem.
  • Nothing is committed to git yet.
